# 桌面版本与打包

适用：桌面应用的首版打包、新版本迭代与本地交付。开发、修复、验收和打包按本次用户指令判断。

## 触发条件

- 首次完整桌面产品交付默认包含本地打包，验收通过后生成约定产物；未限定时使用下述三种交付类型。用户明确要求仅源码、可行性验证或其他受限产物范围时按其要求处理，不把未提打包推断为仅源码交付。
- 尚未进入首次完整交付的增量开发，以及后续日常修改或 Bug 修复，仅完成相关验证；没有用户明确的打包或版本迭代要求时，不自动递增产品版本号、不生成交付包，也不每轮询问是否打包。必要的类型检查、测试和编译构建照常按影响范围执行。
- 用户明确要求“生成首版安装包”“打包交付”、生成新版本或更新产品版本号等，即视为已授权本轮打包。按任务意图判断，不要求固定句式；记录目标版本、平台和架构，已有授权持续覆盖本轮修复与复验，无需每次重问。
- 新版本可以是修订版本或小版本；不因改动大小、Bug 修复完成、测试通过或版本字段被工具改动就推断用户已确认迭代。
- 仅方案或评审任务只分析交付要求，不实际更新版本或打包。现有项目规则与本次指令冲突时，按用户已明确的要求处理，指出需要同步的项目约定。

## 默认三种交付类型

| 类型 | 内容 | 核对方式 |
|---|---|---|
| 便携目录 | 可直接运行的程序目录，含必要依赖与资源 | 在约定环境从目录启动，确认版本及核心流程 |
| 便携 ZIP | 同版本便携目录的压缩包，保留完整运行结构 | 解压到独立测试目录后启动，核对资源与核心流程 |
| 安装程序 | 使用项目安装工具链生成的安装包；Windows 示例为 Setup EXE | 在隔离环境按项目安装流程验证安装、启动、版本与相关功能 |

默认生成上述三类产物；用户明确只要求某一类或另有范围时按其指令执行。各类产物使用同一版本和目标架构。Windows 命名示例为 `App_x64_1.2.3_portable/`、`App_x64_1.2.3_portable.zip`、`App_x64_1.2.3_setup.exe`；实际产品名、版本、平台、架构和输出位置按项目确定。其他平台采用对应的程序目录和安装包格式，不强套 EXE。某类产物受平台或工具限制时说明缺口，不默默减少约定的交付类型。

## 迭代与验证顺序

1. 按上述触发条件确定是否进入本轮版本交付，并记录产物范围、目标平台和架构；未触发时按验证参考交付当前修改结果。
2. 进入版本交付后，根据指定版本或项目约定确定目标版本，核对唯一版本源及必要的锁文件、清单和界面显示。首版使用已确定的初始版本；版本迭代按已确认目标更新。
3. 按 [验证与验收范围](verification.md) 完成最终候选的源码与功能验收，核对需求覆盖与实际结果；打包产物在第 5 步核对。
4. 验收通过后使用现有工具链构建并生成约定产物，核对依赖、资源与产品图标；Web 技术桌面应用还须检查开发 Bridge 及启动入口已排除在交付包外，生产运行不启动或暴露 Bridge。
5. 分别核对各类实际产物的版本、启动、应用/安装图标和相关核心流程；安装或持久化行为有改动时覆盖对应回归。使用隔离数据和测试环境，不操作日常配置或设备，也不按产物数量重复整套源码测试。
6. 打包失败时修正原因，重新生成受影响产物并复验；有影响源码或功能验收结果的改动时返回第 3 步。重试不另起版本，不删除旧版有效产物；产物未经验证不能记作通过。
7. 本次约定的产物及适用检查均完成后交付路径、版本和验证结果。无法解除的阻塞明确失败或未验证范围，不声称交付完成。上传发布、安装到用户日常环境等动作按本次授权范围另行处理。
