# 验证与验收范围

适用：确定开发、修改、修复和版本交付时的验证范围、分工与复验时机。沿用目标项目工具链，不内置通用测试框架。

## 从需求识别质量风险

依据使用场景、运行条件和改动影响，识别影响正确性、可用性或选型的质量风险，将适用项转化为可验证标准；开发或修复任务写入当前验收 MD。以下提示按需展开：

- 高吞吐或持续采集：输入速率与突发流量、积压与背压、界面响应和保存能力，以及数据丢失或降采样是否符合需求并可观察。
- 通信与异步任务：超时、取消、断线重连、过期或重复结果、设备确认语义，以及恢复后的状态一致性。
- 长期运行与持久化：内存和资源增长、文件/端口/订阅释放、异常退出后的数据完整性与恢复，以及实际输出结果。

指标与验证条件依据需求、协议、支持环境或必要测量确定；尚无依据时记录假设与覆盖边界。影响关键选型或交付承诺的未知条件，先通过测量、可行性验证或必要澄清解决。具体指标、验证时长及线程、队列、存储等实现方案按项目条件选择。

## 按影响和阶段选择

日常默认执行能检验本次改动的最小充分验证。依据影响范围选择，不只看代码行数，也不在每次编辑后跑全量审核、全部测试或重新打包。

| 本次改动或阶段 | 验证范围 |
|---|---|
| 仅文档、说明或注释 | 内容一致性、链接与差异检查，按需运行相关文档校验 |
| 独立逻辑 Bug 或局部功能 | 定向复现原问题，运行相关单元或集成测试，覆盖直接关联边界 |
| 界面文案、样式、布局或局部交互 | 相关静态检查、必要的定向验证；界面操作和观察仅覆盖受影响页面、状态与尺寸，可按已约定分工交由用户复核 |
| 公共组件、协议、状态机、通信、持久化或权限 | 覆盖受影响调用方与关联链路，按风险扩大回归范围；通信等使用已授权的模拟器或测试环境 |
| 首次完整产品交付、用户明确进入版本迭代或要求整体验收 | 核对完整约定范围，执行全部适用的项目检查与测试套件，逐项审查全部功能界面及相关状态，走通核心用户流程及相关取消、失败恢复与资源释放；按交付范围验证原生能力与实际产物 |

全量验收覆盖本次产品/版本支持范围，不机械运行无关历史脚本或超出授权的硬件操作。缺少环境的适用项列为未验证；未执行的检查不能计为通过。

## 任务验收记录与恢复

- 开发或修复任务实施前，将基本标准与已知审核项先落盘到项目验收 MD，并关联本次需求依据；后续发现新边界时补充依据与审核项，不降低标准迎合实现。
- 同一任务持续更新同一份记录，注明当前阶段、已完成/待处理项、阻塞与恢复条件、下一步及结果适用的代码/候选和环境。小任务可简短追加到现有文件，记录规模与任务相称；只读方案或评审按其约定输出，不自行写文件。
- 上下文压缩、换轮或中止后，先读取当前验收 MD 与相关依据，再核对工作区、实现和运行环境。保留真实执行历史；没有结果的计划或尝试继续标为未执行/未验证。
- 核对既有证据仍适用的范围，继续待处理项并复验变化部分。重建交付包时核对实际运行代码、资源和相关流程，版本号或文件名相同不能单独证明旧结果适用；确认未受影响的结果可复用。
- 工具中止遵循相应工具的恢复规则；换轮不代表保护已解除。恢复界面操作前重新确认实际画面与已授权目标一致，不沿用旧坐标或仅凭后台状态输入，不绕过仍生效的中止。

## 细化审核项与覆盖

基本标准、细化审核项及结果在当前验收 MD 中统一维护，依据需求和原型、结合实际实现补充。业务/API、交互与视觉分别体现预期与覆盖结果；每项包含验证对象、相关状态或条件、预期结果和执行方式，执行后补充实际结果与必要证据。

- 完整验收列出全部功能入口、页面、页签、菜单和弹窗，展开各自相关状态及视觉检查点；日常修改只列受影响部分。不能只列核心计算或主页面，把其他功能界面合并成一句“布局正常”。
- 从真实界面逐项操作，并实际查看相关画面；交互和视觉分别标明通过、失败或未验证。点击、数据回填或脚本断言通过，不等于文字、列表、弹层等显示正确。
- 按风险选取典型与边界数据、尺寸和相关状态；同类重复数据可以选择代表样本，无需穷举全部输入与尺寸组合。长文本、多行内容、密集列表或滚动容器存在时，检查内容完整性、遮挡和操作可达性。
- 业务链路按实际能力及契约列项；Bridge 与原生通道的覆盖见适用架构参考。鉴权检查、单个成功请求或测试总数不能代表全部业务能力通过。
- 交付前对照需求、界面清单和实际记录核对覆盖。未操作、未观察或未核对的适用项保留为未验证；完整验收存在失败或未验证项时只能交代阶段结果，不能称为完整产品验收通过。

## 用户复核与重复执行

- 日常自动验证与用户手动复核按任务分工记录。用户尚未反馈的操作/视觉检查列为待复核，可以交付修复代码及已执行结果，不称为整体产品验收通过。用户复核完成后记录实际反馈，升版与打包仍按桌面交付触发条件处理。
- 失败后先定位原因，修正并定向复验原问题及受影响流程。无新变更、失败或其他风险依据时，复用仍有效的检查结果。
- 版本阶段在稳定的最终候选上集中完成全量验收；修复过程中先做相关复验，候选收敛后再完成最终全量检查。全量验收后又有影响结果的代码改动时重新确认覆盖范围，不用旧结果宣称新候选通过。
- 桌面产物核对及其与源码检查的分工见 [桌面版本与打包](desktop-packaging.md)。
