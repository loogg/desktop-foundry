# 结构设计与审核

以下方法用于判断界面结构、框图的表达粒度及方案是否支持用户任务。

## 从任务形成结构

| 分析方面 | 需要作出的判断 |
|---|---|
| 用户任务 | 哪些内容需要同时可见，哪些适合逐步出现，哪些属于独立视图。 |
| 内容关系 | 输入、操作与结果如何关联，哪些信息需要比较或共同更新。 |
| 信息主次 | 核心任务与高频内容如何突出，辅助内容放在哪里。 |
| 使用条件 | 数据密度、操作方式、目标屏幕如何影响分区、尺寸与滚动关系。 |

先设计整体结构，再展开各模块。简单模块可直接在整体图中说明，复杂模块补充内部结构；跨页面的关键任务补充简短流程，必要时为不同显示条件绘制相应结构。

框图用区域块及文字说明职责和内容。输入区说明输入类别，结果区说明表达形式及数据含义，例如“折线图：时间与测量值的变化趋势”或“表格：逐项记录明细”。按钮、文本框及曲线形状等细节留到交互原型中表达。

## 简单示例

以下为结构框图示例，具体设计按实际需求调整。

整体结构：

```text
+------------------+--------------------------+
| 输入与配置区     | 结果展示区               |
| 数据、参数       | 趋势图与明细             |
+------------------+--------------------------+
| 执行状态与反馈                              |
+---------------------------------------------+
```

结果展示模块：

```text
+----------------------+----------------------+
| 趋势：折线图         | 明细：表格           |
+----------------------+----------------------+
```

图旁简要说明关键操作如何引起区域更新，例如“执行后更新趋势和明细，选中明细记录时定位相应趋势数据”。初始、处理中、成功、空结果或失败等状态按本次需求选择，说明其触发与反馈。

## 审核结构方案

对照需求和使用过程检查：

| 维度 | 审核问题 |
|---|---|
| 需求覆盖 | 核心任务是否都有对应内容、操作与反馈，是否存在无依据的模块。 |
| 范围取舍 | 对照原始需求与主要取舍，是否遗漏重要场景或能力，是否因自行设定的假设而过早收窄范围。 |
| 任务闭环 | 从进入、输入到获得结果及后续操作，必要路径是否连贯。 |
| 信息组织 | 主次、分组与区域关系是否清楚，相关内容是否便于联动与比较。 |
| 展示形式 | 图表、表格或其他形式是否适合数据含义，能否支持用户判断。 |
| 状态与反馈 | 本次需要表达的状态是否考虑到，异常是否有合理的恢复方式。 |
| 显示与操作 | 目标尺寸、内容密度及必要操作方式是否支持方案。 |
