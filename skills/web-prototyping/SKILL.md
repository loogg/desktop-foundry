# Web 交互原型

用户要求和已有项目约定优先。Agent 根据需求、已有资源和当前环境选择设计方向与实现方式。

新建原型连续完成设计、实现与检查；修改和验收沿用当前方案。普通修改检查本次改动及直接影响，整体验收检查约定范围；仅设计、仅评估或仅提供提示词时，按约定范围交付。

## 1. 理解并补全需求

分析用户描述、提供的文档、已有原型与项目资源，判断目标用户、场景、任务、输入输出、约束和评审内容是否明确，按缺失内容选择处理方式。

| 需求情况 | 处理重点 | 读取材料 |
|---|---|---|
| 只有主题方向 | 展开主要场景、能力分支与典型任务，再确定范围。 | [主题探索](references/discovery/topic-discovery.md) |
| 目标明确，功能或流程有缺口 | 围绕既定目标定向补全缺失环节。 | [定向补全](references/discovery/gap-completion.md) |
| 功能明确，仅界面组织或交互表达未定 | 设计模块关系、展示形式与操作反馈。 | [结构设计与审核](references/structure-and-review.md) |
| 已有完整需求或设计 | 核对冲突、遗漏与执行约束，沿用已明确的决定。 | 按发现的问题选用相关参考；无缺口时直接据其设计。 |
| 局部修改 | 分析本次改动及直接影响。 | 按涉及内容选用相关参考。 |

按模块分别判断补全深度，可以组合使用不同方法；已明确的部分直接沿用。需求完整程度与领域知识的不确定性分别判断。

- **共用判断**：区分用户明确要求、资料依据与设计假设。知识有不确定性时结合已有资料与必要搜索核实，记录来源和适用条件；无法核实的部分说明假设及影响。普通设计取舍自主决定，影响核心方向且无法合理推断的缺口才向用户澄清。
- **实现深度**：功能范围与实现深度分别判断。不接入真实设备或服务，本身不足以作为省略任务相关界面与流程的理由；明确的用户范围和约束优先。
- **记录结论**：将需求、必要依据、假设与验收要点写入原型方案文档，默认使用 `prototype-plan.md`，已有适用文档则沿用，位置遵循当前项目约定。

## 2. 明确设计系统

- **沿用与补充**：优先采用用户提供或项目已有的适用规范，仅补充本次缺口；没有适用规范时生成 `DESIGN.md`。已有 `design.md` 等文件沿用原位置和名称。
- **格式与职责**：新建或按 Google Labs 格式调整 `DESIGN.md` 时，读取 [官方规范](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) 执行。它用 Markdown 与可选 YAML frontmatter 表达设计系统，记录设计 token、视觉原则、通用布局与组件规则；需求、业务流程和具体页面结构保存在原型方案中。
- **规范审核**：对新建或调整的规范，以资深 UI 设计师的视角检查其是否支持需求与关键任务、共用规则是否一致，以及是否存在影响设计的缺口，修正后复核。规范随原型设计迭代更新，实际效果继续在原型中验证。

## 3. 绘制界面结构框图

- **结构设计**：根据需求、用户任务、目标显示条件和设计规范，自主设计页面与模块的空间组织，为需要设计或调整的界面绘制 ASCII 结构框图。设计方法与表达粒度见 [结构设计与审核](references/structure-and-review.md)。
- **保存与恢复**：实现前将框图、关键流程与状态说明、结构审核结论保存到原型方案文档。开始实现、继续修改或上下文压缩后恢复任务时，读取当前方案与设计规范；发生设计变更时同步更新对应文档。平台无法保存额外文件时，提供可复制的 Markdown 作为后续依据，并说明保存限制。

## 4. 审核结构方案

- **对照审核**：以资深 UI 设计师的视角，对照需求与关键任务，按 [结构设计与审核](references/structure-and-review.md) 中的审核问题检查方案。
- **修正与复核**：结构存在缺口时返回第 3 步修改并重新审核；发现需求理解或依据有误时返回第 1 步，更新受影响的设计规范与结构。记录主要问题、修正与审核结论，通过后进入实现，按用户约定连续推进。

## 5. 实现界面与交互

- **制作依据**：制作或修改原型源码前，先读取并遵循 [制作约定与示例](references/mock-and-components.md)。新建原型时，同时读取 [TSX 结构模板](templates/App_Prototype.tsx)，以其职责划分和注释结构为起点，按当前技术栈转换，省略未使用的分区；已有原型沿用现有结构，落实本次涉及的约定。
- **内容与状态**：按真实功能组织页面与视图，以业务含义命名。同一功能的相关视图与关键状态优先共用页面或组件，局部变化可用状态切换，弹窗、抽屉与临时提示按需表达；视图是否拆分以功能差异和评审需要判断，避免仅为局部状态重复整页。
- **产品画面**：只放产品本身会呈现的元素，用具体、合理且相互对应的业务内容展示效果。关键操作呈现对应的状态和反馈；额外的 mock 切换、状态推进等演示控制放在代码或独立调试入口。产品本身的帮助与提示正常设计。
- **制作方式**：依据审核后的方案，根据本次评审目标选择实现程度，按需使用 mock 与控件占位并说明范围，将设计规范落实到共用样式与组件。

## 6. 检查实际效果与交付

- **源码核对**：检查原型源码前，先读取 [制作约定与示例](references/mock-and-components.md)，核对本次范围内的顶部说明、mock 数据与模拟行为、控件占位及相关注释是否与实际实现一致；本次新建的原型同时核对模板中适用的职责划分和注释结构。
- **效果检查**：按本次任务范围检查当前可运行成果，核对需求、结构方案、设计规范与界面及交互的一致性，验证关键用户任务和所需状态的实际表现。结合当前画面或截图检查布局、层级、间距、裁切与重叠，实际操作关键流程。

发现问题后，返回相关环节修正并复查，维护相应代码说明。交付可继续编辑的源码或项目入口、运行或预览方式、原型方案与设计规范，以及实际检查范围和结论；无法实际检查的内容如实说明。
