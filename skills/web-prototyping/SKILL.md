# Web 交互原型

用户要求和已有项目约定优先。Agent 根据需求、已有资源和当前环境选择设计方向与实现方式，按本次任务范围使用以下指导。

## 1. 明确需求与设计规范

- **需求与资源**：分析需求、提供的文档与已有原型，明确关键用户任务、使用场景、目标显示条件和本次评审内容。优先采用用户提供的设计规范，未提供时查找项目已有规范及适用资源。
- **形成规范**：已有适用规范直接沿用，缺口按本次需求补充。没有适用规范时，在原型目录生成 `design.md`，记录实际采用的颜色、字体、间距、组件状态与反馈、共用布局及自适应规则；已有原型依据当前设计整理本次涉及的规则。平台无法保存额外文件时，交付同等设计说明。
- **规范审核**：对新建或调整的规范，以资深 UI 设计师的视角检查其是否支持需求与关键任务、共用规则是否一致，以及是否存在影响设计的缺口，修正后复核。规范随原型设计迭代更新，实际效果继续在原型中验证。

## 2. 表达产品界面与交互

- **内容与状态**：按真实功能组织页面与视图，以业务含义命名。同一功能的相关视图与关键状态优先共用页面或组件，局部变化可用状态切换，弹窗、抽屉与临时提示按需表达；视图是否拆分以功能差异和评审需要判断，避免仅为局部状态重复整页。
- **产品画面**：只放产品本身会呈现的元素，用具体、合理且相互对应的业务内容展示效果。关键操作呈现对应的状态和反馈；额外的 mock 切换、状态推进等演示控制放在代码或独立调试入口。产品本身的帮助与提示正常设计。
- **制作方式**：根据本次评审目标选择实现程度，按需使用 mock 与控件占位并说明范围，将设计规范落实到共用样式与组件。源码中的数据组织、控件示意和代码说明采用下方制作参考中的约定。

## 3. 检查实际效果

按本次任务范围检查当前可运行成果，核对需求、设计规范与界面及交互的一致性，验证关键用户任务和所需状态的实际表现。发现问题在本次授权范围内修正并复核；无法实际检查的项目如实说明。
