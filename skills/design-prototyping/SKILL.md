# 设计画布原型

用户要求和已有项目约定优先。下文以 Figma 术语描述，其他平台按设计意图采用对应能力。

新建原型连续完成设计、检查与修正；修改和验收沿用当前方案。普通修改检查本次改动及直接影响，整体验收检查约定范围；仅设计方案、仅评估或仅提供提示词时，按约定范围交付。

## 1. 理解并补全需求

分析用户描述、提供的文档、已有设计与项目资源，判断目标用户、场景、任务、输入输出、约束和评审内容是否明确，按缺失内容选择处理方式。

| 需求情况 | 处理重点 | 读取材料 |
|---|---|---|
| 只有主题方向 | 展开主要场景、能力分支与典型任务，再确定范围。 | [主题探索](references/discovery/topic-discovery.md) |
| 目标明确，功能或流程有缺口 | 围绕既定目标定向补全缺失环节。 | [定向补全](references/discovery/gap-completion.md) |
| 功能明确，仅界面组织或交互表达未定 | 设计模块关系、展示形式与操作反馈。 | [结构设计与审核](references/structure-and-review.md) |
| 已有完整需求或设计 | 核对冲突、遗漏与执行约束，沿用已明确的决定。 | 按发现的问题选用相关参考；无缺口时直接据其设计。 |
| 局部修改 | 分析本次改动及直接影响。 | 按涉及内容选用相关参考。 |

按模块分别判断补全深度，可以组合使用不同方法；已明确的部分直接沿用。需求完整程度与领域知识的不确定性分别判断。

- **共用判断**：区分用户明确要求、资料依据与设计假设。知识有不确定性时结合已有资料与必要搜索核实，记录来源和适用条件；无法核实的部分说明假设及影响。普通设计取舍自主决定，影响核心方向且无法合理推断的缺口才向用户澄清。
- **表达深度**：功能范围与原型表达深度分别判断。通信、计算或复杂控件可以通过示意数据、状态和交互说明表达，缺少真实实现本身不足以排除相关界面与流程。

## 2. 明确设计规范

- **沿用与补充**：优先采用用户提供或项目已有的适用规范、样式、组件和资源库，仅补充本次缺口；没有适用规范时，明确本次采用的视觉方向与共用规则，再落实到设计中。
- **共用内容集中放置**：设计系统收纳本项目实际采用的样式、组件、必要状态和共用布局规则；自适应可用规则与局部示意表达，不为说明适配复制整套产品界面。组件共性写入 Description，具体实例只补差异；已有资源与说明有效时直接引用。
- **规范文档按需提供**：用户已提供 `DESIGN.md` 时沿用；用户要求，或后续转代码、跨 Agent 复用需要文本规范时，按需保存并维护。新建或按 Google Labs 格式调整该文件时，读取 [官方规范](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) 执行，明确采用的规范来源并与画布实际设计保持一致。仅画布协作且已有规范足够时，可直接沿用，不强制另建文件。需求与具体页面结构记录在原型方案中。

## 3. 形成并审核结构方案

- **结构设计**：根据用户任务、目标显示条件和设计规范，自主组织页面与模块。采用简短 ASCII 框图或画布低保真区域块表达整体及关键模块，已有清晰结构可沿用；方法与表达粒度见 [结构设计与审核](references/structure-and-review.md)。
- **审核与修正**：以资深 UI 设计师的视角，对照原始需求、主要取舍和关键任务，按参考中的审核问题检查结构。发现需求理解或依据有误时返回第 1 步，结构缺口则修改方案并复核；通过后进入完整界面制作。
- **保存与恢复**：制作前保存需求依据、假设、范围、结构、关键流程与状态及审核结论。沿用已有方案；有本地项目时可用 `prototype-plan.md`，纯画布任务可用原生方案说明区并关联设计节点。选择一处作为当前方案，记录主要决定及必要理由。继续修改或上下文压缩后恢复任务时读取当前方案与规范，设计变化时同步更新受影响的记录。

## 4. 按内容职责组织文件

制作、修改或验收设计画布原型前，先读取 [组织与标注示例](references/organization-and-expression.md)，结合示例落实下方约定。具体 Page 划分、组件表达与标注文案按本次需求和已有设计适配。

- **Page 划分**：先看需求与已有文件，按内容划分 Page，例如“产品界面”“设计系统”“数据模型”“理论与计算依据”。内容少时合并，独立且复杂时拆分；名称默认中文，沿用已有适用结构，不固定建齐目录或创建空页。公式编辑器、协议配置等真实产品功能仍属于产品界面。
- **界面与状态**：同一功能的相关视图与关键状态优先放在同一 Section，以业务含义命名。整页变化用 Frame，控件变化优先用组件状态，弹窗等临时内容按需用浮层表达；不为每个局部变化复制整页。

## 5. 呈现产品效果与交互意图

- **产品画面**：只放产品本身会呈现的界面元素，用具体、合理且相互对应的业务内容展示效果。设计讨论、开发待办和为演示额外添加的“样例已载入”“推进事件”等内容不进入产品画面；产品本身的帮助、导入样例等功能正常设计。
- **复杂组件示意**：曲线、仪表盘等可用接近预期效果的组件占位，表达布局、数据含义和交互意图。用 Annotation 标明原型参考范围及正式开发需专用实现的部分；通信、计算可用示意数据表达。

## 6. 在需要的位置补充说明

- **Annotation 适用于任何 Page**：产品界面、设计系统、数据模型、理论依据中，有难从设计本身理解的规则就按需标注。用原生 Annotation 就近关联控件、区域、界面 Frame 或说明对象；标注不作为产品 UI 元素。平台不支持时放在对应画板外，并明确关联对象。
- **说明只补缺口**：补充特殊行为、样例范围和未确认假设，不重复画面已表达的信息。跨 Page 的业务依据，在相关对象的标注中注明位置或链接。

## 7. 检查实际效果与交付

按本次范围核对需求、结构方案、设计规范与当前设计的一致性，查看最新画面或截图，检查内容、视觉、状态、组织与标注；已制作的关键交互也实际检查。发现问题返回相关环节修正并复查。

交付可编辑设计文件或项目入口、原型方案及相关规范的位置或内容，以及实际检查范围和结论；制作了交互演示时附入口。无法实际检查的内容如实说明。
