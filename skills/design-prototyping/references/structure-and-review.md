# 结构设计与审核

以下方法用于在完整界面制作前判断结构、表达粒度及方案是否支持用户任务。

## 从任务形成结构

| 分析方面 | 需要作出的判断 |
|---|---|
| 用户任务 | 哪些内容需要同时可见，哪些适合逐步出现，哪些属于独立视图。 |
| 内容关系 | 输入、操作与结果如何关联，哪些信息需要比较或共同更新。 |
| 信息主次 | 核心任务与高频内容如何突出，辅助内容放在哪里。 |
| 使用条件 | 内容密度、操作方式与目标屏幕如何影响分区、尺寸和滚动关系。 |

先设计整体结构，再展开关键模块，简单模块可直接在整体图中说明。多界面任务补充页面之间的关键流程与必要状态；已有设计只改局部时，沿用清晰的现有结构。

## 表达方式与粒度

可用 Markdown 中的 ASCII 框图，也可在画布中使用低保真区域块与简短说明。选择适合本次任务的一种表达作为结构依据，已有有效表达时直接引用。

区域说明职责、输入类别、展示形式与数据含义，例如“折线图：数值随时间变化”或“表格：逐项记录明细”。具体按钮、输入框和曲线形状在界面制作中表达。需要说明的触发、联动、前后状态与反馈写在图旁；这些说明按画布约定放在产品界面之外。

以下为结构框图示例，具体设计按实际需求调整。

```text
+------------------+--------------------------+
| 输入与配置区     | 结果展示区               |
+------------------+--------------------------+
| 执行状态与反馈                              |
+---------------------------------------------+
```

结果模块可进一步说明：

```text
+----------------------+----------------------+
| 趋势：折线图         | 明细：表格           |
+----------------------+----------------------+
```

## 审核问题

| 维度 | 审核问题 |
|---|---|
| 需求覆盖 | 核心任务是否都有对应内容、操作与反馈，是否存在无依据的模块。 |
| 范围取舍 | 对照原始需求与主要取舍，是否遗漏重要场景或能力，是否因自行设定的假设过早收窄。 |
| 任务闭环 | 从进入、输入到获得结果及后续操作，必要路径是否连贯。 |
| 信息组织 | 主次、分组与区域关系是否清楚，相关内容是否便于联动与比较。 |
| 展示形式 | 图表、表格或其他形式是否适合数据含义，能否支持用户判断。 |
| 状态与反馈 | 必要状态是否有表达，异常是否有合理的恢复或返回方式。 |
| 显示与操作 | 目标尺寸、内容密度及必要操作方式是否支持方案。 |
