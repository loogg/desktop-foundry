# 设计画布原型（design-prototyping）

帮助 Agent 组织和表达 UI 设计成果：按内容划分 Page、呈现产品画面、表达复杂组件，以及在需要的对象旁标注说明。配合所选平台和设计插件使用。

[SKILL.md](SKILL.md) 包含可直接执行的约定；[组织与标注示例](references/organization-and-expression.md) 仅在需要具体例子时读取，无需复制进提示词。

按任务选择执行方式：从需求制作默认在一次任务中完成设计与验收闭环；完善已有设计默认修改并做局部检查；需要闭环或多轮修改后的整体检查时，使用“整体验收”模板。

## 在 Figma 中使用

基础搭配为 **design-prototyping + Figma + design-system-ops**。发送前选中 Skill 并附上对应插件，替换模板中的方括号；选填行可以删除。

需要额外设计支持时，再附上 **Taste** 或 **Impeccable**，并将模板首句中的“Figma 和 design-system-ops”替换为“Figma、design-system-ops 和 Taste”或“Figma、design-system-ops 和 Impeccable”。插件中的能力按本次任务选用。

### 从需求制作

```text
使用 $design-prototyping，配合 Figma 和 design-system-ops 插件，根据以下需求制作用于后续开发的 Figma UI 原型。

需求：[需求描述或文档]
目标位置：[Figma 文件或文件夹链接]
补充约束（选填）：[使用场景、风格参考、已有资源等]

在一次任务中连续完成以下流程：
1. 制作：根据需求完成约定范围的界面、关键状态和必要说明，完成后立即进入第 2 步。
2. 审查：以资深 UI 设计师的角色进行内容与视觉审查。内容核对需求覆盖、文案与数据、状态、组织与标注；视觉查看当前截图，检查层级、排版、间距、一致性、裁切与重叠。已制作的关键交互也实际检查。通过则进入第 4 步，有问题则进入第 3 步。
3. 修正：直接修复问题，复核受影响的界面、状态和共用组件，然后返回第 2 步，基于最新成果重新审查。
4. 交付：只有本次约定范围内的验收项全部通过后，才最终答复，提供可编辑的 Figma 文件链接与验收结论；制作了交互演示时附上入口。

过程中可以汇报进展，自行推进，不逐轮等待我确认，不在制作阶段结束时最终交付。若有无法自主解决的阻塞，说明阻塞项和已完成范围，不宣称验收通过。
```

### 完善已有设计

```text
使用 $design-prototyping，配合 Figma 和 design-system-ops 插件，完善以下 Figma UI 原型。

现有设计：[文件或节点链接]
本次改动：[需求或问题]
补充约束（选填）：[需要保留的内容、风格参考等]

1. 修改：查看现有设计，沿用适用资源与约定，完成本次改动。
2. 局部检查：仅检查本次改动和直接受影响的布局、文案、状态及共用组件；涉及已有交互时检查对应行为。修复发现的问题，不主动启动整体验收或扩大修改范围。
3. 交付：局部检查完成后提供更新后的文件链接，简要说明修改与检查范围；相关交互演示附上入口。若我另有闭环验收要求，先完成指定范围的验收再交付。无法检查的项目如实说明，不将局部检查称为整体验收通过。
```

若本次修改也需要闭环审查，在模板末尾追加：“本次改动及其影响范围也要执行内容与视觉审查；有问题直接修正后重新审查，直到该范围内验收通过再交付。无法自主解决的阻塞如实说明，不宣称通过。”

### 多轮修改后的整体验收

```text
使用 $design-prototyping，配合 Figma 和 design-system-ops 插件，以资深 UI 设计师的角色，对以下原型进行整体内容与视觉验收，并修正发现的问题。

现有设计：[文件或节点链接]
验收依据：[当前需求、已确定的设计方向或相关文档]
验收范围（选填）：[需要验收的页面或功能；留空按当前原型整体检查]

在一次任务中连续完成以下流程：
1. 明确依据：读取现有设计与验收依据，沿用既定需求和设计方向，确定本次验收范围。
2. 整体审查：以资深 UI 设计师的角色检查整个验收范围，不只看最近修改的部分。内容核对需求覆盖、文案与数据、状态、组织、组件示意及标注；视觉查看当前截图，检查层级、排版、间距、跨界面一致性、裁切与重叠。已制作的关键交互也实际检查。通过则进入第 4 步，有问题则进入第 3 步。
3. 修正：直接修复问题，复核受影响的界面、状态和共用组件，然后返回第 2 步，基于最新成果重新审查。
4. 交付：只有约定范围内的验收项全部通过后，才最终答复，提供文件链接、验收结论与主要修正；相关交互演示附上入口。

过程中可以汇报进展，自行推进，不逐轮等待我确认。若有无法自主解决的阻塞，说明阻塞项和已完成范围，不宣称验收通过。
```

## 使用其他平台

将所用平台的插件或工具附到消息中，填入实际名称，并选择任务类型。新建默认闭环，修改默认局部检查，验收按指定范围闭环。

```text
使用 $design-prototyping，配合 [平台的插件或工具名称]，在 [平台名称] 中完成以下 UI 原型任务。

任务类型：[新建 / 修改 / 验收，选择一项]
需求或验收依据：[需求、改动描述或相关文档]
目标位置：[现有项目、文件或保存位置]
补充约束（选填）：[使用场景、风格参考、已有资源等]

将 Figma 术语按设计意图对应到本平台，沿用已有适用约定，按以下流程执行：
1. 准备成果：新建任务完成约定设计；修改任务完成本次改动；验收任务读取现有设计和验收依据。然后进入第 2 步。
2. 检查：新建、验收和明确要求闭环的修改，以资深 UI 设计师的角色做内容与视觉审查：核对需求、文案与数据、状态和说明，查看当前截图检查层级、排版、间距、一致性、裁切与重叠，实际检查已制作的关键交互；普通修改仅检查改动和直接影响。检查通过则进入第 4 步，有问题则进入第 3 步。
3. 修正：直接修复问题。新建、验收或明确要求闭环的修改，返回第 2 步重新审查；普通修改只复核修正及其直接影响，通过后进入第 4 步，不扩大为整体验收。
4. 交付：对应范围的检查或验收通过后，提供可继续编辑的项目入口、结果与检查范围；制作了交互演示时附上入口。新建、验收及明确要求闭环的修改，在闭环完成前不最终交付。

过程中可以汇报进展，自行推进。若有无法自主解决的阻塞，说明阻塞项和已完成范围，不宣称通过。
```
