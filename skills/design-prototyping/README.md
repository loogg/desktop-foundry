# 设计画布原型（design-prototyping）

按约定需求范围制作、完善或验收设计画布中的 UI 原型，表达产品界面、关键状态与交互意图，供设计评审与后续开发参考。

版本 `0.5.0`，作者 `loogg`。[SKILL.md](SKILL.md) 提供需求分流、设计规范、结构审核、方案保存及画布组织与表达的流程；本页提供完整闭环调用模板。[组织与标注示例](references/organization-and-expression.md) 由 Agent 在制作、修改或验收前读取，具体内容按本次需求和已有设计适配。

## 提示词模板

按任务选择执行方式：从需求制作默认在一次任务中完成设计与验收闭环；完善已有设计默认修改并做局部检查；需要闭环或多轮修改后的整体检查时，使用“整体验收”模板。

基础搭配为 **design-prototyping + Figma + design-system-ops**。发送前选中 Skill 并附上对应插件，替换模板中的方括号；选填行可以删除。

需要额外设计支持时，可在“设计能力”字段指定 **Taste**、**Impeccable** 或其他适用能力，并附上对应插件。所选能力按本次产品类型与设计载体使用，辅助视觉方向、排版和检查；画布编辑由所选设计平台完成，已有规范与资源优先。

### 从需求制作

```text
使用 $design-prototyping，配合 [Figma 或本次设计平台] 和 design-system-ops 插件，根据以下需求制作用于后续开发的 UI 原型。

需求：[需求描述或文档]
目标位置：[设计文件、节点、文件夹或项目链接]
设计规范（选填）：[已有设计系统、资源库、DESIGN.md、规范内容或链接]
设计能力（选填）：[Taste、Impeccable 或其他适用能力]
补充约束（选填）：[使用场景、风格参考、已有资源等]

在一次任务中连续完成以下流程：
1. 制作：按 Skill 判断需求完整程度，明确设计规范，形成并审核结构方案，保存方案后完成约定范围的界面、关键状态和必要说明，完成后立即进入第 2 步。
2. 审查：以资深 UI 设计师的角色进行内容与视觉审查。内容核对需求覆盖、结构方案与规范一致性、文案与数据、状态、组织与标注；视觉查看当前截图，检查层级、排版、间距、一致性、裁切与重叠。已制作的关键交互也实际检查。通过则进入第 4 步，有问题则进入第 3 步。
3. 修正：返回相关需求、结构或界面设计环节直接修复问题，同步更新受影响的方案与规范，复核相关界面、状态和共用组件，然后返回第 2 步，基于最新成果重新审查。
4. 交付：只有本次约定范围内的验收项全部通过后，才最终答复，提供可编辑的设计文件或项目入口、原型方案与相关规范的位置或内容，以及验收结论；制作了交互演示时附上入口。

过程中可以汇报进展，自行推进，不逐轮等待我确认，不在制作阶段结束时最终交付。若有无法自主解决的阻塞，说明阻塞项和已完成范围，不宣称验收通过。
```

### 完善已有设计

```text
使用 $design-prototyping，配合 [Figma 或本次设计平台] 和 design-system-ops 插件，完善以下 UI 原型。

现有设计：[设计文件、节点或项目链接]
本次改动：[需求或问题]
原型方案（选填）：[方案文档或画布内方案说明位置]
设计规范（选填）：[已有设计系统、资源库、DESIGN.md、规范内容或链接]
设计能力（选填）：[Taste、Impeccable 或其他适用能力]
补充约束（选填）：[需要保留的内容、风格参考等]

1. 修改：读取现有设计、方案与规范，沿用适用资源与约定；需要调整结构时，更新相关方案并审核，再完成本次改动。
2. 局部检查：仅检查本次改动和直接受影响的布局、文案、状态及共用组件；涉及已有交互时检查对应行为。修复发现的问题，不主动启动整体验收或扩大修改范围。
3. 交付：局部检查完成后提供更新后的设计文件或项目入口及相关方案、规范说明，简要说明修改与检查范围；相关交互演示附上入口。若我另有闭环验收要求，先完成指定范围的验收再交付。无法检查的项目如实说明，不将局部检查称为整体验收通过。
```

若本次修改也需要闭环审查，在模板末尾追加：“本次改动及其影响范围也要执行内容与视觉审查；有问题直接修正后重新审查，直到该范围内验收通过再交付。无法自主解决的阻塞如实说明，不宣称通过。”

### 多轮修改后的整体验收

```text
使用 $design-prototyping，配合 [Figma 或本次设计平台] 和 design-system-ops 插件，以资深 UI 设计师的角色，对以下原型进行整体内容与视觉验收，并修正发现的问题。

现有设计：[设计文件、节点或项目链接]
验收依据：[当前需求、已确定的设计方向或相关文档]
原型方案（选填）：[方案文档或画布内方案说明位置]
设计规范（选填）：[已有设计系统、资源库、DESIGN.md、规范内容或链接]
设计能力（选填）：[Taste、Impeccable 或其他适用能力]
验收范围（选填）：[需要验收的页面或功能；留空按当前原型整体检查]

在一次任务中连续完成以下流程：
1. 明确依据：读取现有设计、方案、规范与验收依据，沿用既定需求和设计方向，确定本次验收范围。
2. 整体审查：以资深 UI 设计师的角色检查整个验收范围，不只看最近修改的部分。内容核对需求覆盖、结构方案与规范一致性、文案与数据、状态、组织、组件示意及标注；视觉查看当前截图，检查层级、排版、间距、跨界面一致性、裁切与重叠。已制作的关键交互也实际检查。通过则进入第 4 步，有问题则进入第 3 步。
3. 修正：返回相关设计环节直接修复问题，同步更新受影响的方案与规范，复核相关界面、状态和共用组件，然后返回第 2 步，基于最新成果重新审查。
4. 交付：只有约定范围内的验收项全部通过后，才最终答复，提供可编辑的设计文件或项目入口、验收结论与主要修正，以及相关方案与规范的位置或内容；相关交互演示附上入口。

过程中可以汇报进展，自行推进，不逐轮等待我确认。若有无法自主解决的阻塞，说明阻塞项和已完成范围，不宣称验收通过。
```
